# Farm Chokchai Check-in — Role & Area Setup

โปรเจกต์นี้แยกเป็น 3 ส่วนหลัก

1. **Firebase Authentication** สำหรับล็อกอิน
2. **Firestore collection `users`** สำหรับเก็บ role และสิทธิ์รายคน
3. **Google Sheet + Apps Script** สำหรับเก็บพื้นที่เช็กอิน, logs, สถานะ geofence และตาราง many-to-many สำหรับการ assign user/area

## หน้าแต่ละส่วน

- `index.html` — หน้าเข้าสู่ระบบ
- `admin.html` — หน้าดูพื้นที่ทั้งหมด / แผนที่ / ปุ่มไปหน้า QR
- `qr_code.html` — สร้าง QR ของแต่ละพื้นที่
- `setarea.html` — หน้า Settings ของพื้นที่แบบมีแผนที่ (ใช้ชื่อ SetArea ให้ชัดเจน)
  - เลือกผู้ใช้ด้วย checkbox จาก Firestore collection `users` เฉพาะ role `admin` และ `masteradmin`
- `users.html` — masteradmin ใช้กำหนด role และ assign สิทธิ์รายคน
- `settings.html` — alias ที่พาไป `setarea.html` เพื่อรองรับลิงก์เก่า
- `user/checkin.html` — หน้า user เช็กอิน
- `logs.html` — ดูประวัติการเช็กอิน

## Role matrix

### masteradmin
- เห็นทุกหน้า
- เข้า `users.html` ได้
- เข้า `setarea.html` ได้
- เห็นพื้นที่ทั้งหมด
- บันทึกและ assign user/area ได้

### admin
- เห็นหน้า `admin.html`, `qr_code.html`, `logs.html`
- เห็นพื้นที่ที่ถูกอนุญาตตาม `visibleRoles` / `visibleUsers`
- **ไม่เข้า `users.html`**
- **ไม่เข้า `setarea.html`**

### user
- เห็นแค่ `user/checkin.html`
- ใช้เช็กอินตาม area ที่ได้รับสิทธิ์

## การ assign สิทธิ์พื้นที่

ในเวอร์ชันนี้แยกเป็น 2 ชั้น

- `assign` / `visibleRoles` — กำหนด role ที่เห็นพื้นที่ เช่น `masteradmin,admin`
- `email` / `visibleUsers` — รายชื่อ email ของผู้ใช้ที่ถูกผูกกับพื้นที่นี้แบบหลายคนต่อ 1 area

ระบบจะสร้าง sheet เพิ่มอีกตัวคือ `AreaAssignments` สำหรับความสัมพันธ์แบบ many-to-many:
- 1 คนดูได้หลายพื้นที่
- 1 พื้นที่มีผู้ใช้ได้หลายคน

หน้า `setarea.html` จะดึงรายชื่อจาก Firestore collection `users` แล้วแสดงเฉพาะ role `admin` และ `masteradmin` ให้เลือกเท่านั้น

## ต้องแก้ Apps Script ไหม

ต้องแก้ใน `apps-script/Code.gs` เพื่อให้
- อ่าน/เขียนพื้นที่จากชีต `location`
- sync ความสัมพันธ์ลง `AreaAssignments`
- ดึงรายชื่อ `users`
- บันทึก `logs`

สิ่งที่ควรเช็กคือ:
1. `SPREADSHEET_ID`
2. ชื่อชีต `location`, `AreaAssignments`, `Users`, `Logs`
3. ให้ Web App ของ Apps Script deploy เรียบร้อย

## เรื่องรายชื่อ Firebase Auth

หน้าเว็บฝั่ง client จะดึงรายชื่อจาก Firestore `users` เป็นหลัก  
ถ้ารายชื่อไม่ขึ้น ให้เช็กว่า user นั้นมี document อยู่ใน collection `users` และ role เป็น `admin` หรือ `masteradmin`


## Tab component

หน้า admin / users / logs / qr_code / setarea ใช้ component `app-tabs` ร่วมกันเพื่อให้ tab หน้าตาและพฤติกรรมตรงกันทุกหน้า


## Template workbook

ไฟล์ `data/Area_Setup_Template.xlsx` มีชีตตัวอย่างสำหรับ `location`, `AreaAssignments`, `Users`, และ `Logs` เพื่อใช้เป็นต้นแบบเวลาสร้าง Google Sheet ใหม่


## SetArea
หน้า `setarea.html` ต้องโหลด Firebase Auth/Firestore และ `firebase-auth.js` ด้วย เพื่อให้ `FirebaseRole.currentSession()` ทำงานได้ครบ

ถ้าเห็น error แนว ๆ `You do not have permission to access the requested document` ตอน save:
- ตรวจว่า Apps Script web app deploy เป็น `Execute as me`
- หรือแชร์ Google Sheet ตัวจริงให้ account ที่รันสคริปต์เข้าถึงได้
- ตรวจว่า `SPREADSHEET_ID` ใน `Code.gs` ตรงกับไฟล์ Google Sheet จริง

## 🔧 สิ่งที่แก้ไขในรอบนี้ (สำคัญมาก กรุณาอ่านก่อน deploy)

### ปัญหาที่พบ
1. **กด "บันทึก" พื้นที่ใหม่ในหน้า SetArea แล้วเขียนทับพื้นที่เดิม** ไม่เพิ่มแถวใหม่
2. **คอลัมน์ `qr_code` ในชีต `location` ว่างเปล่าทุกแถว** ไม่เคยถูกเขียนค่าจริง
3. **ปุ่ม "ดู QR" ในหน้า Admin** บางครั้งพากดูพื้นที่ผิดจากแถวที่กดจริง (ใช้ค่าจำใน localStorage ทับ URL)

### สาเหตุที่แท้จริง
- ฟังก์ชันแปลงข้อมูล (`normalizeArea`) ทั้งในหน้า SetArea และไฟล์ `common.js` เมื่อพบแถวที่ยังไม่มีรหัส `qr_code` (เช่นข้อมูลเก่าที่กรอกตรงใน Google Sheet โดยไม่ผ่านระบบ) จะใส่ค่า fallback เป็นคำว่า `"qr_code"` **เหมือนกันทุกแถว** ทำให้ระบบมองว่าทุกพื้นที่คือพื้นที่เดียวกัน เวลาบันทึกจึงเขียนทับกันไปเรื่อยๆ
- ฝั่ง Apps Script (`Code.gs`) ฟังก์ชัน `saveLocation` ไม่ได้ป้องกันกรณีนี้ไว้ตั้งแต่ต้น
- หน้า `qr_code.html` มี logic จำค่าพื้นที่ล่าสุดไว้ใน `localStorage` ที่บางเงื่อนไขไปแทรกทับค่าจาก URL

### สิ่งที่แก้ไขแล้ว
1. **`apps-script/Code.gs`**
   - เพิ่มฟังก์ชัน `generateUniqueQrCode()` สร้างรหัสพื้นที่ที่ไม่ซ้ำกันโดยอัตโนมัติ (รูปแบบ `AREA-YYYYMMDDHHMMSS-XXXX`)
   - แก้ `saveLocation()` ให้แยกแยะชัดเจนระหว่าง "สร้างใหม่" (ไม่มี `originalAreaId` ส่งมา) กับ "แก้ไขของเดิม" — ตอนสร้างใหม่จะ**ไม่มีทางไปจับคู่ทับแถวเดิมได้เด็ดขาด** แม้รหัสจะว่างหรือซ้ำกันก็ตาม ระบบจะสร้างรหัสใหม่ให้ทันที
   - แก้ `updateAreaAssignments()` และ `deleteLocation()` ให้ใช้คอลัมน์ `qr_code` สอดคล้องกันทั้งหมด (เดิมบางจุดใช้ `areaId` ซึ่งไม่มีอยู่ในชีตจริง)
2. **`assets/common.js`** และ **`assets/page-scripts/setarea.js`**
   - แก้ `normalizeArea()` ไม่ให้ fallback เป็นรหัสคงที่ซ้ำกันทุกแถวอีกต่อไป
   - แก้ `save()` ในหน้า SetArea ให้ตรวจสอบและสร้างรหัสใหม่ที่ไม่ชนกับพื้นที่ที่มีอยู่แล้วทุกครั้งที่กด "+ เพิ่มพื้นที่" แล้วบันทึก
3. **`assets/page-scripts/qr_code.js`**
   - เขียนใหม่ทั้งหมด: `areaId` จาก URL (เช่นจากปุ่ม "ดู QR") จะมีสิทธิ์สูงสุดเสมอ ไม่ถูก localStorage ทับอีกต่อไป
   - เพิ่มข้อความแจ้งเตือนถ้า `areaId` ใน URL หาไม่พบในรายการที่มีสิทธิ์เห็น
4. **`admin.html` / `assets/page-scripts/admin.js`** และ **`setarea.html`**
   - ปุ่ม "ดู QR" ต่อแถว เมื่อกดแต่ละแถวจะพาไปหน้า QR ของพื้นที่นั้นๆ ทันที (เปิดแท็บใหม่)
   - เพิ่มปุ่ม "ดู QR" ในหน้า SetArea ด้วย ทั้งในตารางและในกล่อง "พื้นที่ที่เลือก" เพื่อความสะดวก ไม่ต้องสลับไปหน้า Admin
   - ฟิลด์ `qr_code / areaId` ในฟอร์มแก้ไข จะถูกล็อก (disabled) เมื่อกำลังแก้ไขพื้นที่ที่มีอยู่แล้ว เพื่อป้องกันไม่ให้พิมพ์ทับรหัสโดยไม่ตั้งใจ — แก้ไขได้เฉพาะตอนสร้างพื้นที่ใหม่ (และเว้นว่างได้ ระบบจะสร้างให้อัตโนมัติ)

### ⚠️ ขั้นตอนที่ต้องทำก่อนใช้งานจริง (สำคัญ)
1. **ต้อง deploy `apps-script/Code.gs` เวอร์ชันใหม่นี้ทับของเดิม** ที่ Google Apps Script Editor ของโปรเจกต์ (เปิดไฟล์ในนี้ → copy ทั้งหมด → วางทับใน Apps Script Editor → กด Deploy → New deployment หรือ Manage deployments → แก้ deployment เดิม) ถ้าไม่ deploy ใหม่ บั๊กจะยังเป็นเหมือนเดิมเพราะ frontend เรียก API ตัวเดิมอยู่
2. **ข้อมูลเดิมในชีต `location` ที่คอลัมน์ `qr_code` ว่างอยู่ก่อนหน้านี้** จะถูกระบบมองเป็น "ข้อมูลเก่าที่ยังไม่มีรหัส" — แนะนำให้เปิดหน้า SetArea แล้วกดเลือกพื้นที่นั้น กดบันทึกอีกครั้งหนึ่งครั้ง (ระบบจะสร้างรหัส `qr_code` ให้อัตโนมัติและเขียนกลับเข้าชีต) ก่อนเริ่มสร้างพื้นที่ใหม่เพิ่ม เพื่อให้ปุ่ม "ดู QR" ของแถวนั้นใช้งานได้
3. ทดสอบโดย: เข้าหน้า SetArea → กด "+ เพิ่มพื้นที่" → กรอกข้อมูล → กดบันทึก → ทำซ้ำอีก 2-3 ครั้ง → ตรวจในตารางว่ามีหลายแถวเพิ่มขึ้นจริง (ไม่ทับกัน) → ลองกดปุ่ม "ดู QR" ของแต่ละแถวว่าได้ QR คนละอันจริง

## 🔧 สิ่งที่แก้ไขในรอบนี้ (2) — Logs เช็คอินมีแค่แถวเดียว ไม่เก็บสะสมทุกครั้งที่เช็คอิน

### ปัญหาที่พบ
มีคนเช็คอินเข้ามาหลายครั้ง/หลายคน แต่ชีต `Logs` ใน Google Sheet กลับมีข้อมูลอยู่แค่แถวเดียว (หรือน้อยกว่าจำนวนคนที่เช็คอินจริง) ทั้งที่ปุ่มเช็คอินแสดงผลว่า "บันทึกสำเร็จ" ทุกครั้ง

### สาเหตุที่แท้จริง
1. **ไม่มีการล็อกสคริปต์เวลาเขียนข้อมูล (จุดหลัก)** — `sheet.appendRow()` ของ Apps Script ไม่ใช่คำสั่งที่ atomic จริงๆ เบื้องหลังมันคือ "อ่านแถวล่าสุด แล้วเขียนแถวถัดไป" 2 ขั้นตอนแยกกัน ถ้ามีคนกดเช็คอินพร้อมกันหลายคน (เช่น ทัวร์ทั้งกลุ่มสแกน QR Code เวลาไล่เลี่ยกัน) แต่ละ request ที่ยิงเข้ามาพร้อมกันจะ "อ่านแถวล่าสุด" ได้ค่าเดียวกัน แล้วเขียนทับแถวเดียวกันโดยไม่ตั้งใจ ทำให้ log ของคนอื่นหายไป เหลือรอดมาแค่บางรายการ — โค้ดเดิมไม่มี `LockService` เลยแม้แต่จุดเดียวในทั้งไฟล์
2. **`getSheetByNameOrCreate()` ใช้ `SpreadsheetApp.getActiveSpreadsheet()` แทนที่จะใช้ `SPREADSHEET_ID` ที่กำหนดไว้** — ค่า `SPREADSHEET_ID` ที่ด้านบนของไฟล์ไม่เคยถูกเรียกใช้งานจริงเลย ทำให้ถ้า Apps Script project ไม่ได้ผูก (bound) อยู่กับ Google Sheet ไฟล์เดียวกับที่ผู้ใช้เปิดดู (เช่น ตอนสร้างโปรเจกต์ Apps Script แยกใหม่ หรือคัดลอกโค้ดไปวางในโปรเจกต์อื่นตอน deploy ซ้ำ) ข้อมูลอาจไม่ถูกเขียนลงไฟล์ที่ถูกต้อง

### สิ่งที่แก้ไขแล้ว
1. **`apps-script/Code.gs` → `doPost()`**
   - เพิ่ม `LockService.getScriptLock()` ครอบการทำงานทั้งหมดของ `doPost` (รอคิวได้สูงสุด 10 วินาทีด้วย `tryLock`) บังคับให้ request ที่จะเขียนข้อมูลลง Sheet (เช็คอิน, บันทึกพื้นที่, บันทึกผู้ใช้, แก้ชื่อ log) ถูกประมวลผล **เรียงคิวทีละ 1 รายการเท่านั้น** ไม่มีการแย่งเขียนทับกันอีกต่อไป — แก้ที่จุดเดียวแต่ครอบคลุมทุก action ที่เขียนข้อมูล เพราะทุก action เขียนข้อมูลผ่าน `doPost` ทั้งหมด
   - ถ้าคิวแน่นจริงๆ (รอเกิน 10 วินาที) จะแจ้ง error กลับไปอย่างชัดเจนแทนที่จะค้างเงียบหรือเขียนทับข้อมูล
2. **`apps-script/Code.gs` → `getSheetByNameOrCreate()`**
   - เปลี่ยนมาใช้ `SpreadsheetApp.openById(SPREADSHEET_ID)` แทน `getActiveSpreadsheet()` เพื่อให้สคริปต์เขียนข้อมูลลงไฟล์ Google Sheet ตาม `SPREADSHEET_ID` ที่กำหนดไว้บนสุดของไฟล์เสมอ ไม่ว่าโปรเจกต์ Apps Script จะถูกผูก/ตั้งค่าอย่างไร

### ⚠️ ขั้นตอนที่ต้องทำก่อนใช้งานจริง (สำคัญ)
1. **ตรวจสอบ `SPREADSHEET_ID` ที่บรรทัดบนสุดของ `apps-script/Code.gs` ก่อนเสมอ** — เปิด Google Sheet ไฟล์จริงที่ใช้เก็บ Logs → คัดลอกรหัสจาก URL ส่วนระหว่าง `/d/` กับ `/edit` → เทียบกับค่าที่อยู่ในโค้ด ถ้าไม่ตรงกันให้แก้ในโค้ดให้ตรงกับไฟล์จริงก่อน deploy (ดูวิธีหารหัสได้ที่ `docs/SPREADSHEET_ID.md`)
2. **ต้อง deploy `apps-script/Code.gs` เวอร์ชันนี้ทับของเดิม** เหมือนการแก้ไขรอบก่อน (เปิดไฟล์ในนี้ → copy ทั้งหมด → วางทับใน Apps Script Editor ของโปรเจกต์ → Deploy → Manage deployments → แก้ deployment เดิมเป็นเวอร์ชันใหม่) ถ้าไม่ deploy ใหม่ บั๊กจะยังเป็นเหมือนเดิม เพราะ URL ที่ frontend เรียกอยู่ (`assets/common.js`) ยังชี้ไปที่โค้ดเวอร์ชันเก่า
3. ทดสอบโดย: ลองเปิดหน้าเช็คอินจากมือถือ/แท็บหลายเครื่องพร้อมกัน (หรือให้เพื่อนช่วยกดพร้อมกัน 2-3 คน) แล้วเปิด Google Sheet ดูว่าทุกคนที่เช็คอินมีแถวของตัวเองครบ ไม่มีใครหายหรือถูกทับ

## 🔧 สิ่งที่แก้ไขในรอบนี้ (3) — เช็กอินขึ้น "สำเร็จ" แต่ไม่มีแถวใหม่ใน Logs เลย (ไม่ใช่แค่บางแถวหาย แบบรอบก่อน)

### ปัญหาที่พบ
ผู้ใช้กดเช็กอินที่หน้า `user/checkin.html` หน้าจอขึ้นข้อความว่าสำเร็จและพาไปหน้า `success.html` ตามปกติ แต่เปิด Google Sheet ชีต `Logs` แล้วไม่มีแถวใหม่ถูกเพิ่มเข้ามาเลย — ต่างจากบั๊กรอบที่แล้ว (ที่ยังมีบางแถวถูกบันทึก แค่ไม่ครบทุกคน) รอบนี้บางครั้ง **ไม่มีการเขียนข้อมูลเกิดขึ้นจริงเลยสักครั้ง** ทั้งที่ฝั่ง Apps Script (`saveLog`, `doPost`) ทำงานถูกต้องดีอยู่แล้วจากการแก้ 2 รอบก่อนหน้า

### สาเหตุที่แท้จริง
ใน `assets/page-scripts/user-checkin.js` ฟังก์ชัน `performLocationLookup()` มีอยู่ 2 เส้นทางหลังจากตรวจว่าผู้ใช้อยู่ในพื้นที่ (geofence) แล้ว:

1. **เส้นทางปกติ** (เก็บพิกัดครบ 3 ตัวอย่างแล้วเฉลี่ย) → พาไปหน้า `processing.html` ก่อน ซึ่งหน้านี้เป็นจุดเดียวในระบบที่เรียก `common.addLog()` (ยิง POST ไปหา Apps Script จริงๆ) แล้วค่อย redirect ไป `success.html` **ต่อเมื่อบันทึกสำเร็จเท่านั้น**
2. **เส้นทางลัด** (ถ้า GPS แม่นยำกว่า 10 เมตรตั้งแต่ตัวอย่างแรก — เกิดได้บ่อยมากถ้าสัญญาณดี/อยู่กลางแจ้ง) → โค้ดเดิม `window.location.href = "../success.html"` **พาไปหน้า success.html ตรงๆ ทันที โดยข้าม processing.html ไปเลย**

เพราะมีแค่ `processing.html` เท่านั้นที่เรียก `common.addLog()` (ดูได้จากการ grep ทั้งโปรเจกต์ — `success.html`/`success.js` ไม่เคยเรียก `addLog` เลย แค่อ่านค่าเก่าจาก `localStorage["last_checkin"]` ที่ถูกตั้งไว้จากการเช็กอินครั้งก่อนๆ เท่านั้น) เส้นทางลัดนี้จึง **ไม่มีการส่งข้อมูลไปเขียนชีต Logs เลยแม้แต่ครั้งเดียว** แต่ผู้ใช้ยังเห็นข้อความ "เช็กอินสำเร็จ" เพราะหน้า success.html ขึ้นข้อความสำเร็จแบบ static เสมอ ไม่ได้ตรวจสอบอะไรจริง — และยิ่งทำให้สับสนเพราะถ้าเคยเช็กอินสำเร็จไปแล้วครั้งก่อนหน้า (ผ่าน processing.html) หน้า success.html จะโชว์ชื่อ/เวลาของ "ครั้งก่อน" ค้างอยู่ ทำให้ดูเหมือนเพิ่งบันทึกใหม่ทั้งที่ไม่ใช่

พบบั๊กรูปแบบเดียวกันอีกจุดใน `assets/page-scripts/checkin-auth.js` (หน้า `auth.html` ซึ่งเป็นหน้าทดสอบของแอดมิน ไม่ได้อยู่ในโฟลว์หลักของ user ตามที่เอกสารด้านบนระบุไว้) — ฟังก์ชัน `doCheckIn()` เรียก `common.addLog()` แบบไม่ `await` แล้ว `location.href` เปลี่ยนหน้าทันที ซึ่งมักจะตัด request ที่ค้างอยู่ทิ้งกลางคันเพราะเป็น multi-page app ไม่ใช่ SPA

### สิ่งที่แก้ไขแล้ว
1. **`assets/page-scripts/user-checkin.js`**
   - เปลี่ยนเส้นทางลัด (accuracy ≤ 10 เมตร) ให้พาไป `../processing.html` เหมือนเส้นทางปกติทุกประการ แทนที่จะพาไป `../success.html` ตรงๆ — ตอนนี้ทุกเส้นทางต้องผ่าน `processing.html` (เรียก `addLog()` จริง รอผลลัพธ์ ตรวจ `ok:false`) ก่อนถึงจะถึงหน้า success ได้เสมอ ไม่มีทางลัดที่ข้ามการบันทึกอีกต่อไป
   - ปรับข้อความสถานะระหว่างทางให้ตรงกับความจริงว่า "ระบบกำลังบันทึกข้อมูล...กำลังนำไปหน้าถัดไป" แทนคำว่า "ตรวจสอบสำเร็จ!" เฉยๆ เพื่อไม่ให้เข้าใจผิดว่าบันทึกเสร็จแล้วทั้งที่ยังไม่ได้บันทึก
2. **`assets/page-scripts/checkin-auth.js`** (หน้า `auth.html`)
   - แก้ `doCheckIn()` ให้เป็น `async` แล้ว `await common.addLog(...)` ตรวจ `res.ok === false` ก่อน ค่อย redirect ไป `success.html` เฉพาะตอนบันทึกสำเร็จจริง ถ้า error จะโชว์ข้อความผิดพลาดแทนที่จะเงียบๆ พาไปหน้าสำเร็จ

### ⚠️ ขั้นตอนที่ต้องทำก่อนใช้งานจริง (สำคัญ)
1. ไฟล์ที่แก้รอบนี้เป็นไฟล์ฝั่ง frontend ล้วนๆ (`assets/page-scripts/*.js`) **ไม่ต้อง deploy Apps Script ใหม่** สำหรับรอบนี้ — แค่อัปโหลด/refresh ไฟล์เว็บ (`user-checkin.js`, `checkin-auth.js`) ขึ้น hosting เดิมที่ใช้อยู่ (เช่น GitHub Pages / Firebase Hosting) ให้ทับของเดิม
2. ทดสอบโดย: เปิดหน้า `user/checkin.html` เช็กอินในพื้นที่ที่สัญญาณ GPS ดีมากๆ (เช่น อยู่กลางแจ้งโล่งๆ ที่ accuracy มักจะดีกว่า 10 เมตรตั้งแต่ครั้งแรก) สัก 3-5 ครั้งติดกัน แล้วเปิด Google Sheet ชีต `Logs` ดูว่ามีแถวใหม่เพิ่มขึ้นครบทุกครั้งจริง (ก่อนหน้านี้เคสนี้คือเคสที่มักจะไม่ถูกบันทึกเลย)
